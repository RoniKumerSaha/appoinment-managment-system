An explicit `CONSTRAINT admin_user_clinic_id_fkey` form would require dropping and re-adding the column (since `ADD COLUMN IF NOT EXISTS` doesn't accept a constraint name in place), or a separate `DROP CONSTRAINT IF EXISTS + ADD CONSTRAINT` pair — and the migration runner ships `0013_clinic_anchor.down.sql` which already drops the FK implicitly with the column. - **W30 — Concurrent second `INSERT INTO clinic` race on the singleton invariant:** Two parallel transactions each inserting one row could both see the empty index page and both commit, with the unique violation only firing on COMMIT — at which point one transaction gets 23505 and the other commits. This is the same race every UNIQUE constraint has; the index doesn't make it worse. SERIALIZABLE isolation or a `BEFORE INSERT` trigger could close the door, but both add cost and complexity that the singleton invariant doesn't need (the product is a single-clinic admin tool — second-clinic-INSERT is an operator/seed bug, not a hot path). - **W31 — Pre-migration state with zero clinic rows:** If migration 0013 runs against a DB where the `clinic` table is empty (no singleton row yet), the backfill `UPDATE admin_user SET clinic_id = (SELECT id FROM clinic LIMIT 1)` silently sets `clinic_id = NULL` for every admin row, and the subsequent `SET NOT NULL` then raises `23502` (not_null_violation). The forward migration would fail loudly — that's the correct behavior — but the operator-facing error message is "not_null_violation on clinic_id" rather than the more helpful "no clinic row exists, run 01_minimum seed first." A `DO $$` precheck that `EXISTS (SELECT 1 FROM clinic)` and raises a custom exception could improve the message. ## Deferred from: code review of spec-1-1-create-edit-deactivate-branches (E1-S1, 2026-09-14)

- **W35 — `SELECT ... FOR UPDATE` on `branch` does NOT block `INSERT INTO appointment` (booking-vs-deactivate TOCTOU):** The PATCH deactivate path holds `SELECT ... FOR UPDATE` on the branch row inside a transaction. Per Postgres MVCC, an `INSERT INTO appointment (branch_id, ...)` only takes a `ROW SHARE` lock on the parent row (FK validation), which is compatible with `RowExclusive` (FOR UPDATE) — they don't block. The deactivate's conflict check (`SELECT 1 FROM appointment WHERE branch_id = $1 AND start_datetime > now() AND status = 'Scheduled' LIMIT 1`) is therefore a best-effort snapshot read against the booking transaction, not a serialization point. The current lock DOES block admin-vs-admin races on the same branch (the main cause of conflicts in this admin-tool domain). To fully close the booking-vs-deactivate race, the booking transaction must take a branch-row lock of its own (`FOR SHARE` or `FOR UPDATE` on `SELECT ... FROM branch WHERE id = $1`) before the appointment INSERT. Reopen when E3-S1 (booking core) lands — verify the booking path takes such a lock, or add `pg_advisory_xact_lock(hashtext(branch_id::text))` on both sides. The route file's header comment (`apps/api/src/routes/admin-branches.ts:15-32`) explicitly documents this scope-of-lock caveat for the next maintainer.
